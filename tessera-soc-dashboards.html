            Example dashboards

            Four dashboards security teams build every month

            Each one ships with a synthetic export in a different file format, so you can watch the same pipeline read TSV, JSON, a two-sheet workbook and XML. Open one, then pin, remove or swap charts — the next load of that schema remembers what you did.

            For everyone

            Tessera turns a security export into the dashboard an analyst would have built — and says why.

            Security teams live in exports. EDR consoles, vulnerability scanners, identity providers and cloud posture tools all have an Export button, and most of those files never reach a SIEM. Someone opens them in Excel, builds pivot tables and pastes screenshots into a monthly report. Tessera reads the file, works out what each column means in security terms, builds the dashboard, explains every chart, and learns from what the analyst changes.

            How it works, in four steps

            1. Drop the file. Any of eight formats. Tessera finds where the records are, even inside nested JSON, a multi-sheet workbook or an XML report.
            2. Understand the columns. Each column gets a security meaning: IP address, MITRE ATT&CK technique, severity, identity, asset, CVE. If it guesses wrong, you correct it once and it remembers.
            3. Check before thinking. Cells that try to steer an AI ("ignore previous instructions"), spreadsheet formulas and hidden scripts are quarantined. Names and addresses are masked before any model could see them.
            4. Build and explain. A skill — a template for one kind of dashboard — plus retrieved knowledge and your past edits decide which charts appear. Each chart carries a one-line reason and a score.

            What you get

            A live dashboard
            Charts, an ATT&CK matrix, entity graphs and tables, each with the reason it was chosen. Pin, remove or swap any of them.
            The spec
            A JSON description of the dashboard. It can be versioned, diffed, reviewed and re-rendered in another tool — the dashboard is a view of it.
            Code export
            The same widget as ECharts, Recharts, Tremor, Chart.js, React Flow or Cytoscape code, for teams that want it inside their own portal.
            A report production
            A PDF built from the spec, white-labelled for MSSP clients.
            Memory
            Your corrections, pins and removals, remembered per file layout, so month two starts where month one ended.

            What it isn't

            • Not a SIEM. No collection pipelines, no retention, no correlation rules. It works on files you already have.
            • Not live monitoring in version 1. Files, not streams. Connectors come after the file workflow is proven.
            • Not an autonomous responder. It proposes dashboards. It never blocks an IP, closes a ticket or sends a report without a person.
            • Not general BI. It does security data deeply and nothing else. That focus is the product.

            How your data is handled

            The free tier runs entirely in the browser tab — this prototype is that tier. Paid tiers run in your own tenant or on your own servers. When a model is used, it receives column names, counts and three masked sample rows, never the records themselves. Every file carries a Traffic Light Protocol label: examples are TLP:CLEAR, your own files default to TLP:AMBER and never leave the tab.

            Glossary

            Spec
            The JSON document that describes a dashboard. The model may only suggest edits to it; it never writes code.
            Skill
            A small data-only template for a kind of dashboard: which column meanings it needs, which charts it favours, how many it allows.
            Knowledge pack
            A curated body of reference material — ATT&CK, CVSS bands, export profiles, dashboard patterns — that retrieval draws from.
            Retrieval (RAG)
            Finding the knowledge relevant to this file's columns and handing it to the planner, with a citation for anything it changes.
            Fingerprint
            A hash of the column names. Two exports from the same tool share one, which is how layouts are recalled.
            Quarantine
            A cell that looks like an injection, formula or script. It's shown as text and withheld from any model.
            Adapter
            The code that turns one spec widget into one library's chart.
            TLP
            Traffic Light Protocol 2.0, the sharing label security teams already use: CLEAR, GREEN, AMBER, AMBER+STRICT, RED.

            The prototype caps at 50,000 rows. The service pushes anything larger into DuckDB and plans against aggregates, so a 2 GB firewall log costs the planner the same as a 2 MB one.

            Profiler

            Detection runs in a fixed order so that stronger evidence wins. Value patterns first: at least 80% of sampled values must match (IPv4, CVE, ATT&CK ID, hash, email, URL, timestamp). Then header hints, each gated by a value check — a column called port must hold integers from 0 to 65535. Then cardinality decides between category, identifier and free text.

            GroupMeanings
            NetworkIPv4, IPv6, port, domain, URL
            Identity & assetidentity, email, asset
            ThreatATT&CK technique, ATT&CK tactic, detection name, CVE ID, CVSS score, file hash
            Signaltimestamp, severity, outcome, country
            Genericnumber, category, identifier, free text

            A correction overrides detection by column name and persists. In production each (header, value sample, correction) triple becomes training data for a small column classifier that replaces the heuristics once it beats them on the eval set.

            Knowledge and retrieval

            Retrieval answers one question: what do we already know that applies to a file shaped like this? The query is never the data. It's a schema signature — column names, their meanings, cardinalities and row count.

            PackContentsRefreshedUsed for
            ATT&CKTechniques, sub-techniques, tactics, namesEach ATT&CK releaseTactic enrichment, matrix layout, coverage gaps
            Vulnerability intel productionCVE → CVSS, CISA KEV flag, EPSSDailyRanking CVEs by exploitation, not just score
            Export profilesColumn signatures of common tool exportsWhen a tool is onboardedRecognising the source, suggesting a skill
            Dashboard patternsAnalyst-written notes on how to show a threat (spray, beaconing, exposure)CuratedSmall, cited boosts to specific widgets
            Your historyPast schemas and the specs your team keptOn every saveLayout recall; few-shot examples for the planner

            Pipeline

            1. Build the signature: src_ip (IPv4) · rule_name (detection) · mitre_technique (ATT&CK) · 402 rows.
            2. Hybrid search: pgvector cosine on the embedded signature plus BM25 on column tokens; reciprocal-rank fusion; top 6.
            3. Hand the chunks to the planner with ids. Every patch the model proposes must cite a chunk id or a rule id, or it's rejected.
            4. Retrieval boosts are capped at +0.15 per widget, so knowledge nudges the plan without overriding the skill or the analyst.

            The prototype replaces step 2 with a lexical score — 65% overlap of column meanings, 35% overlap of column-name tokens, threshold 0.35 — and shows its work in the Retrieval tab. Guards: every chunk is tenant-scoped, tenant history never crosses tenants, and retrieved text is quoted as data; a chunk containing instruction-like text is dropped at index time.

            Planner

            score(widget) = base(kind, meaning)          // rule table, 0.40–1.00
              + learned(signature)          // your pins/removals, bounded ±0.60
              + skill.boost[kind]           // −1…+1
              − 1 if kind ∈ skill.suppress
              + retrieval boost             // cited patterns, ≤ 0.15

keep if score ≥ 0.45 or pinned · KPI row first · table last
cap at skill.maxWidgets · pack into 12-column rows, first fit

            In production a model then reviews the spec. It receives the schema, three masked rows, the current spec and the retrieved chunks, and may return only an RFC 6902 JSON Patch:

            [
  { "op": "replace", "path": "/widgets/4/title",
    "value": "Failed sign-ins by source IP", "cite": "pat-spray" },
  { "op": "add", "path": "/widgets/-",
    "value": { "kind": "hour", "encoding": { "t": "timestamp" } },
    "cite": "rule:hour|timestamp" }
]

            The validator allows add, replace and remove under /widgets only, checks every value against the spec schema (Zod), requires a citation, and caps a patch at eight operations. Rejected patches are logged as eval cases.

            Widgets are addressed by stable ids derived from kind and column, so feedback and patches survive re-planning.

            Skills

            FieldMeaning
            requiresColumn meanings the file must have; missing one caps fit at 50%
            optionalMeanings that raise fit from 70% towards 100%
            boostWidget kind → number in −1…+1
            suppressWidget kinds this skill never shows unless pinned
            maxWidgets2–16, KPI row and table included

            Lifecycle: draft → validate → sign (organisation key or Sigstore) → publish → tenants pin a version. Skills are data only; any other field, such as script or html, is rejected. Custom chart code is a separate, reviewed adapter path.

            Phases

            1. Validate. Ten conversations with MSSP and SOC leads; collect 30 sanitised exports. They become the eval set.
            2. MVP — the MSSP monthly report. CSV/TSV, XLSX and JSON; three skills; ECharts and shadcn/ui; PDF out; Docker on-prem.
            3. Team and MSSP. Tenancy, saved dashboards, scheduled reports, white-label, signed skills, knowledge index.
            4. Sovereign. Air-gapped bundle, local model, SAML, exportable audit log.
